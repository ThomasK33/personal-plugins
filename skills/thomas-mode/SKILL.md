# Thomas mode

Paths are relative to this skill's directory (`skillDir` in the `agent_skill_read` result).

When you load this skill only for its Amendments (a pstack or egm step that runs without `/thomas-mode`), skip step 2 below, and apply only the "Amendments to plugin steps" rules for the steps you run.

1. Load the `pstack-in-xum` skill from the `fux-plugins` plugin. It maps pstack's Cursor names to Xum. Before you follow an egm skill, also load `egm-in-xum` from `fux-plugins`.
2. Load `pstack:poteto-mode` with `agent_skill_read` and follow it, with the rules below.

Precedence: `~/.xum/AGENTS.md`, then his memory (`/memories/global/user-workflow-preferences.md`, read it with the `memory` tool at task start and after every context rollover), then this skill, then poteto-mode and its playbooks. This skill does not repeat AGENTS.md or memory. At the same two times, also read these memory sections: "Shared host: processes and cleanup", "Shell scripting" and "mise and toolchains" in `/memories/global/coder-workspace-gotchas.md`, and "Background bash and restarts" in `/memories/global/xum-mux-recovery.md`. For each tool that the task will run, grep `~/.xum/memory/global/tool-and-library-facts.md` with `bash`. That file is the disk copy of `/memories/global/tool-and-library-facts.md`. The `memory` tool has no grep, and its `/memories/...` paths are not on disk. Keep the grep output small, for example with `grep -n -i '<tool>' ~/.xum/memory/global/tool-and-library-facts.md | cut -c1-200`. Then read the matching lines with `file_read`, with the line number as the offset and a small limit. A plain grep for a common tool, such as `gh`, prints more than 16 KB and lines over 1024 bytes, so the bash tool fails or filters its output. (A root read 4 memory files and none of these sections. The `pgrep -f` trap, the mise-shim trap with 33 "not trusted" outputs, and the `pack.mjs` trap all came back, though memory describes each one.)

## Where poteto-mode yields

- **PRs.** "Land", "get it merged", "ship it", or his ship prompt is the request to open a PR and merge it. "Fix" alone is not. Then poteto-mode's "Opening a PR" runs.
- **Review rounds.** AGENTS.md section 5 caps review at six rounds per PR. It replaces any round count in a playbook. Its section 5.3 clean-context advisor runs before each merge decision, at any round count. A verifier does not replace it.
- **Subagents.** Pass `model: "anthropic:claude-opus-5-5"` on every `task` unless a pstack role line says otherwise.
- **Reply style.** Follow both AGENTS.md "Plain English" and poteto-mode "Writing the reply". Where they differ, AGENTS.md wins.

## Shipping

His ship prompt is the definition of done:

1. Commit on a branch from fresh `origin/main`.
2. When the prompt asks for a bug bash, run it. Fix what it finds and repeat until a round finds no regression, incomplete fix or new defect in changed code. Bugs that main had before the loop started follow "Findings after a feature PR" under "Swarm-verify once". Attach the last report as an artifact.
3. Open the PR and wait for checks.
4. Merge through the merge queue when CI is green, both Codex lanes are clean on the exact head, and an independent final review finds no issues.
5. Report landed per the Shipping amendment "Stop at the ceiling".

- **Merge is your job** once he asked for it. Never end with "PR is open, do you want me to merge?". `--admin` needs his explicit word in this chat. A bypass list is not that word.
- **Pixel does not block.** Ignore the `Pixel / Review` status.
- **A silent Codex blocks.** At run start, check the repo's recent PRs for a Codex comment or review. A reaction is not evidence. When at least one recent trigger got no Codex answer within an hour and no trigger got one, ask him once, at the start. Offer a waiver for the whole run or for each PR, plus one or both substitutes: a reviewer lane on each exact head from the `interrogate reviewers` model whose family differs from the worker's, and required status checks on main when it has none. Otherwise re-request the review once after about an hour. If Codex is still silent, report it and ask. Merge without a Codex verdict only on his word, for that PR or for the run. (A 40-PR run merged on a whole-run waiver with only Anthropic reviewers, and main had no required checks.)
- **Fix now.** Fix a concrete defect in or next to the work in this branch, or in a sub-agent PR that you drive to merged. Do not offer to file an issue. Defer only scope creep that he agrees to defer. Memory defines scope creep as "a fix bigger than the original change". A valid review finding follows "Findings after a feature PR" under "Swarm-verify once". A known gap that he agreed to defer as scope creep is a deferral: open its tracking issue before the merge, and link it from one contract line instead of listing its conditions. (A data-loss gap lived only in closed issues and a 7,954-character README bullet until a trail review flagged it.)

## Doing the work

- **Never hand him a step you can do.** Use `gh`, the Xum CLI, and the other CLIs to check state, find IDs, and merge. Before you post a decision card, test each option against AGENTS.md, his memory, this skill, the active playbook and his answers in this run. When only one option complies, act on it and report, unless a rule asks for his answer or waiver by name. When his answer changes a memory default in general, edit that memory in the same turn. An override that he scopes to one PR or run stays in that run, and memory keeps the default. (Three of five cards in one run had only one compliant option, and a re-enqueue cap stayed in memory after he answered "no cap".)
- **Prefer the real fix.** Cut scope, delete code, and remove a race by construction instead of adding a heuristic or a workaround.
- **Tests.** Every brief that writes code names `fux-plugins:test-audit`, `pstack:principle-test-behavior-not-implementation` and `pstack:tdd`, with those plugin prefixes: a bare `tdd` loads a different global skill that teaches test-first work. A plan or brief lists behaviors, never test cases. (In a coder/coder program, Go test lines were a median 2.5 times the product lines, against 1.7 times on other merged Go PRs, and a reviewer's only complaint was the ratio.)
- **Sub-agent memory.** Every child brief says: write no memory file apart from your own `/memories/session/` checkpoint, and put lessons in your report. The root curates those lessons under his memory-hygiene rule, and deletes each claim that a lane later withdraws from every place that holds it. (Child memory edits once filled files with SHAs and run counts, and one saved a bug claim that its lane later withdrew.)
- **Theme toggle.** Every HTML artifact has an Auto / Light / Dark theme toggle at the top right. Copy its markup, CSS and script from [references/theme-toggle.md](references/theme-toggle.md), and follow that file's rules for the rest of the page and its check. When you change that file's markup, CSS or script, run `scripts/test-theme-toggle.sh`. When a skill's runtime or build script makes the page (such as `status-page`, `html-plan`, `pr-walkthrough` or `skill-doctor`), add the toggle there in a coder/fux-plugins PR, or rely on an open coder/fux-plugins PR that already adds it. Never add it to the built file. When that PR has landed, rebuild the page and run the page check from the reference. Until then, publish the built page as it is and link the PR in your report. (He asked for the toggle on every artifact after he saw it on one.)
- **UI and HTML artifacts.** Check at phone width (mobile Safari) and in dark mode before you publish. Apply the `coder-brand` skill to visual output. When you fix a UI bug, find siblings with the same defect and fix them in the same PR.
- **Verification skills.** "Verify and formally verify" means run the repo's verification skill and its formal-verification skill. When the repo has none, create them with `create-verification-skill` and `create-formal-verification-skill`, land them, then fix what they find. When a scratch harness catches a blocker, or a second agent in the same run rebuilds it, add it to the repo's verification skill when the repo has one. Memory points at repo paths, never at a workspace's scratch folder. (The matrices that caught the claudecode.nvim blockers lived only in sub-agent scratch folders. Two agents in one coder/xum run each rebuilt the same loopback model fixture.)
- **Forks in research.** When research ends in "which approach" or "should we build this", write an `html-plan` with the decisions on it. Do not end with an offer.
- **Posts in other repos.** Before you post an issue or comment in another repo, check the draft: each quoted string comes from a grep in an earlier step, each claim about our code is checked, and private code stays out of a public repo. GitHub keeps the edit history, so an edit after posting does not undo a wrong quote. (coder/coder#31758 quoted a notice that our code does not contain.)
- **CI waits.** Every wait starts with two reads: load the `background-monitors` skill, and read the CI-wait bullet of `/memories/global/xum-control-and-config.md` (it starts "task_await on a monitored background bash"). Where the two differ, memory's monitored watcher wins: the root runs one shell or Python poll script as a background `bash` job with a `monitor`. The root ends its turn after it arms the watcher, apart from memory's goal-turn cases (a bounded foreground poll for a short wait that a goal turn must not end on, or `task_await` on a one-shot monitored watcher that prints nothing until it exits). If that `task_await` returns at once, fall back to the foreground poll. A sub-agent (an owner, a verifier or a lane) never waits on a monitor: a busy sub-agent gets `bash.monitor` wakes only after its turn ends, so each wake arrives after its report. It runs a bounded watcher in a foreground bash until the watcher prints its final line, with `timeout_secs` at least 300 s above the watcher's own deadline. The foreground default is 60 s, and a watcher checks its deadline only between polls. When Xum moves that call to the background, the sub-agent keeps waiting on it with `task_await`. Use a foreground poll in the root only where memory allows one. Every wait uses the same done rule. The wait reads the exact head's results and is done only when each expected check has a final result. An expected set that is empty or cannot be worked out is not a pass: stop waiting and report it. Memory's `github-pr-review-merge.md` (gh and API traps) has the API details. (One sleep loop exited on the empty rollup right after a push. An owner's 14:48 watcher match reached it at 17:27, after its merge-ready report, and caused "nothing changed" reports. A root that skipped both reads blocked first in `task_await`, then in a `while pgrep -f` loop, and lost about 76 minutes to timeouts.)
- **Long or fan-out work.** Keep one status page, an HTML artifact named `status.html`. Fewer words, bigger visuals. You design the page: pick the layout, diagrams, charts and tables that show this work best, and change them when the work changes. Do not use the `status-page` skill's fixed renderer unless he asks for it. Every version shows five things: a headline with the one thing he must know or do now, what needs him (decisions and his own steps), what runs now with the workspace ID of each sub-agent or workspace, every follow-up with what it waits on (kept until it is done or dropped), and the "Updated" and "Next check" times in exactly this ISO 8601 UTC form: `2026-11-13T13:21:07Z`. Read the current time with the bash tool on every rebuild, never from memory. "Next check" is the soonest time you expect to rebuild: the next heartbeat, a watcher's deadline, or the next expected sub-agent report. Write "none" only when nothing runs and the work waits only on him or is done. A small inline script checks the clock once the page has loaded and every 30 seconds. It shows "Overdue: the agent missed its next check" when the clock passes "Next check" by 10 minutes, or when it cannot read "Next check", and nothing when "Next check" is "none". Escape `&`, `<`, `>`, `"` and `'` in all outside text, such as PR and issue titles, before it goes into the HTML. Never put outside text, escaped or not, inside a `<script>` or an `on…` attribute: a handler bound with `addEventListener` reads it from a `data-` attribute or the element's text. Take each count and state of outside work, such as PRs, checks or issues, from a read made for this rebuild, never from the previous version. Rebuild and publish it on every check, heartbeat and state change. Inline all CSS, scripts and images. Never put secrets or URLs with credentials on it. Add no free-text box, spinner or moving bar. The only button that sends text is an optional answer button for a decision or step that you did not also ask in the chat. It calls `window.xum.send` from its click handler. Never edit Xum's `goal.status.html`. When an `<agent-interface>` block in your prompt gives its own rules for `status.html`, follow those where they differ and keep the rest of this rule. (He found the fixed renderer too rigid, and liked free-form artifacts built on "Fewer words, bigger visuals".) On his stop order, stop every sub-agent, monitor, and heartbeat. On "wind down", archive the helper workspaces this chat created. Delete one only when he says delete.
- **End every final report with a verdict.** Done or Not done, what merged, and what is still open. No "if you want" offers. Before you write "Done", match every item on the triaged follow-up list to a merged PR, to the deferral tracking issue, or to a reasoned decline in the trail. A fixable in-scope gap, an unexplained failure, or a limit he did not agree to defer makes the verdict "Not done". Two more cases make it "Not done". One is a new user-facing option that lacks a worked example in the main user doc, or a mention in each doc page for its command. The other is a gap that the root's own research or plan named and that the run neither ran nor declined. The report also lists each design call that the run made for him and each new stated limit in user docs, each with the option that the run did not take. (A "Done" report listed an in-scope token gap as a known limit, called a lost backend connection "not explained", and dropped advisor follow-ups the root had promised to carry. A later "Done" passed a new flag with only README table rows and skipped a large-monorepo measurement that the root's own research had named. Its next reply said "as you described" and hid a design call: `--folder .` fails inside `site/`, because the path starts at the repo root.)

### Autopilot

[pstack skills/poteto-mode/playbooks/autopilot-full.md § Run owners in parallel off trunk]

- An order he gives ("land X, then Y") is a merge gate. Owners still work in parallel, but PRs merge in his order. (Dependency and backlog PRs merged before the two skills he named first.)

[pstack skills/poteto-mode/playbooks/autopilot-full.md § Swarm-verify once]

- A fix that answers a verifier's ISSUES verdict, or any edit the root makes itself, is never "wording-only". It gets a new verify brief at the new head, sent to the verifier that the "Verifier model" rule sets. A verifier never stands in for clean Codex lanes on the exact head or for the section 5.3 advisor. At any round count, past the review cap included, a merge without clean Codex lanes on the exact head needs his waiver for that PR, or his whole-run waiver given under "A silent Codex blocks" for a head where Codex gave no answer. Ask for it by name before you enqueue. (A loop merged five PRs on the root's own diff read, and one past six Codex rounds on a verifier's word.) A waiver's stop condition names impact classes (a security flaw, data loss, broken core behavior), never a reviewer's severity label. (A waiver said "a new P1 still stops it", a Codex P2 then turned out to be a token exposure, and the root rewrote his rule without asking.)
- Verifier model. The root sends each verify brief to one fresh `anthropic:claude-opus-5-5` verifier at `xhigh`, on every PR, and reuses it for no later brief. This rule sets the verifier model, not the `swarm workers` row of the AGENTS.md table. No second verifier runs: he ended the `openai:gpt-6.1-sol` verifier on 2026-11-10. When a crash or a refusal ends the verifier, its replacement runs on `anthropic:claude-sonnet-5-5` at `xhigh`. When the ended verifier ran on Sonnet, the replacement runs on Opus, with the brief reworded as defensive checks of our own code ("confirm `down` refuses X"), never attacks. When that Opus verifier also ends that way, the root asks him. The merge waits for the verifier's verdict on the head. When a push replaces a head, the root sends a new brief for the new head. Apart from his stop order, the root stops a verifier only when every head in that verifier's brief has a new head or has merged. A long silent run is normal. The root never replaces a verifier because it is slow or silent. When a verifier looks stuck, the root tells him and he decides. (In November 2026, two blind judges scored 45 and 44 of 48 PR heads that all three models had checked. Opus found 14 of 15 and 18 of 19 valid blockers, Sonnet 12 and 13, and gpt-6.1-sol 8 and 10. No model found a blocker that Opus missed. On the 25 heads with cost data for all three, gpt-6.1-sol cost a median 0.26 USD per check, Sonnet 0.90 USD and Opus 1.44 USD.)
- Findings after a feature PR. A feature PR fixes only blockers and the defects it introduced in its own changed code. A blocker is a security flaw, data loss or broken core behavior. Triage every other valid finding from any source, and every follow-up the root promised to carry, into one list when it arrives, not a log: drop duplicates and fixed items, and mark each item necessary or not. For a feature PR's merge gate, a Codex lane or final review whose only valid findings are on the list counts as clean. After the last feature PR lands, one follow-up workspace builds the necessary items, one PR per area. A follow-up PR fixes what it introduced and what it touches. An older finding that its review raises and that it does not reach goes on the list, and one final sweep PR handles the list: it never starts a new PR chain. At the second follow-up PR in one area, stop and propose a redesign or a narrower scope before any more fixes there. Items not marked necessary are his agreed deferral: one tracking issue, one reason per item. A reasoned decline of an invalid finding is fine, and a finding is invalid only when its problem is not real. (A superblink run chained follow-ups of follow-ups, 4 PRs for one Archive refusal, because each fresh review found older problems near the change, and he called it a massive failure. A second run logged 108 reviewer rows for 10 PRs.)
- A verifier can revert or mutate a claimed fix to see which test turns red. When no test turns red, it reports a minor finding with the fix's trigger, never ISSUES. The owner then decides with `pstack:tdd` and `fux-plugins:test-audit` whether a test is worth adding, or names the check that proves the fix, and that recorded choice closes the finding. (A required test per fix caused 11 of 15 blocking verdicts in a coder/coder program, and its PRs carried about 2.5 test lines per product line.)

[pstack skills/poteto-mode/playbooks/autopilot-full.md § Run the root layer]

- Count an area's findings from every source (verifiers, advisors, Codex and dogfood runs), across every PR and follow-up PR that reopens that area. An area is one shared asset or invariant, such as one credential, across every PR that touches it, not one file or one PR. Write the tally into the trail at each round boundary. At the second round with findings in the area, when that round has no fewer new findings in the area than the first such round, propose to remove the mechanism, as the round-2 rule in his memory says ("If round 2's findings don't shrink"). The tally is a running total for the trail only, and it does not decide this. Command text that echoes user input, such as a paste-ready hint, is a class of mechanism that does not converge. By the fourth review round with findings in one area, stop asking for a waiver per round. Ask the operator one question whose options include narrowing the scope or redesigning that area. When he picks a narrowing or redesign option, write the banned premise, and the premise that the findings share, into every later brief for that area at once. When you close an area, write the banned premise (such as "no proxy for editor state that has no API") into the repo's AGENTS.md in the PR that closes the area (create it if absent), and into every later owner, verifier and lane brief for that area. In a repo you do not own, put it in the closing PR body and every later owner, verifier and lane brief. (openFile's reload code took about 19 Codex rounds over six PRs, and the owner after a "stop adding mechanism" decision added a proxy that regressed. Token handling later drew findings in about 11 PRs, and nobody asked the question. One paste-ready `--folder` hint drew about 8 findings across 5 PRs, and nobody asked it there either, because the root counted per PR.)
- Decide when to stop by the severity of new findings, not by the round count. On security and trust code, do not stop early: late rounds kept finding real P1s. Rounds past six still need his waiver.
- When the same gate false positive blocks a second PR, fix the gate in its own PR. Do not approve the bypass again. This includes a CI infrastructure step, such as a registry download, that fails a second PR: read the failed step's name before any rerun, and open a PR that hardens the step (a retry with backoff, a cache or another tool). Reruns can go on while that PR is open, but it merges before the check becomes required. (One `aube install` registry error got about 30 `gh run rerun` calls in one run.)

[pstack skills/poteto-mode/playbooks/shipping.md § Stop at the ceiling]

- Count a PR as landed only after the post-merge runs on its merge commit have settled and none of them failed, `Required` or not (release jobs included). `success`, `neutral` and `skipped` count as passing. Post-merge workflows can start late, and a PR that adds, removes or renames a workflow changes the set, so check those workflows by name. Report the result. (release-please went red on main during a loop that checked only `Required`.)
