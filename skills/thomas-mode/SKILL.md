## Where poteto-mode yields

- **PRs.** "Land", "get it merged", "ship it", or his ship prompt is the request to open a PR and merge it. "Fix" alone is not. Then poteto-mode's "Opening a PR" runs.
- **Review rounds.** AGENTS.md section 5 caps review at six rounds per PR. It replaces any round count in a playbook. Its section 5.3 clean-context advisor runs before each merge decision, at any round count. A verifier does not replace it.
- **Subagents.** Pass `model: "anthropic:claude-opus-5-5"` on every `task` unless a pstack role line says otherwise.
- **Reply style.** Follow both AGENTS.md "Plain English" and poteto-mode "Writing the reply". Where they differ, AGENTS.md wins.

## Shipping

His ship prompt is the definition of done:

1. Commit on a branch from fresh `origin/main`.
2. When the prompt asks for a bug bash, run it. Fix what it finds and repeat until a round finds no regression, incomplete fix or new defect in changed code. Bugs that main had before the loop started follow the Swarm-verify amendment: each valid one is loop work, in this PR or in a follow-up PR. Attach the last report as an artifact.
3. Open the PR and wait for checks.
4. Merge through the merge queue when CI is green, both Codex lanes are clean on the exact head, and an independent final review finds no issues.
5. Report landed per the Shipping amendment "Stop at the ceiling".

- **Merge is your job** once he asked for it. Never end with "PR is open, do you want me to merge?". `--admin` needs his explicit word in this chat. A bypass list is not that word.
- **Pixel does not block.** Ignore the `Pixel / Review` status.
- **A silent Codex blocks.** At run start, check the repo's recent PRs for a Codex comment or review. A reaction is not evidence. When at least one recent trigger got no Codex answer within an hour and no trigger got one, ask him once, at the start. Offer a waiver for the whole run or for each PR, plus one or both substitutes: a reviewer lane on each exact head from the `interrogate reviewers` model whose family differs from the worker's, and required status checks on main when it has none. Otherwise re-request the review once after about an hour. If Codex is still silent, report it and ask. Merge without a Codex verdict only on his word, for that PR or for the run. (A 40-PR run merged on a whole-run waiver with only Anthropic reviewers, and main had no required checks.)
- **Fix now.** Fix a concrete defect in or next to the work in this branch, or in a sub-agent PR that you drive to merged. Do not offer to file an issue. Defer only scope creep that he agrees to defer. Memory defines scope creep as "a fix bigger than the original change". For a valid review finding from any source (a verifier or lane, an advisor, Codex, a trail review, a bug bash, a PR reviewer or your own check), the loop rule under "Swarm-verify once" wins: fix it in this PR or in a follow-up PR in the same run, and open no issue. A known gap that he agreed to defer as scope creep is a deferral: open its tracking issue before the merge, and link it from one contract line instead of listing its conditions. (A data-loss gap lived only in closed issues and a 7,954-character README bullet until a trail review flagged it.)

## Doing the work

- **Never hand him a step you can do.** Use `gh`, the Xum CLI, and the other CLIs to check state, find IDs, and merge. Before you post a decision card, test each option against AGENTS.md, his memory, this skill, the active playbook and his answers in this run. An override that he scopes to one PR or run stays in that run, and memory keeps the default. (Three of five cards in one run had only one compliant option, and a re-enqueue cap stayed in memory after he answered "no cap".)
- **Prefer the real fix.** Cut scope, delete code, and remove a race by construction instead of adding a heuristic or a workaround.
- **Tests.** Every brief that writes code names the fux-plugins `test-audit` skill and pstack's `principle-test-behavior-not-implementation`, and `owner-rules.md` copies this bullet. A test here is a test function, a subtest or a table row. Before you add or change one, apply the test-audit authoring gate, before the PR opens and before each push that starts a review round. For a new test function or subtest, write the gate's four answers and the failing run of a production break into the trail. For a new row or assertion, write the regression that fails it and its failing run. A plan or brief lists behaviors, never test cases. Each behavior names the one layer that tests it. A test of the same behavior at a second layer needs a failure mode that the first layer cannot reach (the gate's question on existing coverage). A review fix needs no new test when a kept test already fails on the break. Otherwise it gets its test as a new row in an existing table or a new assertion in an existing test, unless no existing test reaches the fixed path. (In a coder/coder program, Go test lines were a median 2.5 times the product lines, against 1.7 times on other merged Go PRs. [pstack skills/poteto-mode/playbooks/autopilot-full.md § Swarm-verify once]

- A fix that answers a verifier's ISSUES verdict, or any edit the root makes itself, is never "wording-only". It gets a new root-briefed verify brief at the new head, sent to the verifier that the "Verifier model" rule sets. When the root regenerates a committed file with a repo tool, such as a lock file, the regenerated-file rule under "Re-check that the verdicts still describe the code" wins. A verifier never stands in for clean Codex lanes on the exact head or for the section 5.3 advisor. At any round count, past the review cap included, a merge without clean Codex lanes on the exact head needs his waiver for that PR, or his whole-run waiver given under "A silent Codex blocks" for a head where Codex gave no answer. Ask for it by name before you enqueue. (A loop merged five PRs on the root's own diff read, and one past six Codex rounds on a verifier's word.) A waiver's stop condition names impact classes (a security flaw, data loss, broken core behavior), never a reviewer's severity label. (A waiver said "a new P1 still stops it", a Codex P2 then turned out to be a token exposure, and the root rewrote his rule without asking.)
- Every verify brief asks for one closing line per requested PR: `VERDICT #<pr> <40-char sha> PASS|ISSUES`. Merge only on a line whose PR and SHA match the head, or on a line that a rule here or in the playbook carries to the head (such as the regenerated-file rule). A missing line means ask again. (A long-lived verifier answered two queued PRs in one turn and reported one.) A verifier that crashed or was refused (a content filter) has no line: start a new verifier as the "Verifier model" rule sets. A reworded brief states defensive checks of our own code ("confirm `down` refuses X"), never attacks. The root's own check never fills the slot. (A verifier died on a content filter, and the root merged on its own replay after it had edited the branch itself.)
- Verifier model. The root sends each verify brief to one fresh `anthropic:claude-opus-5-5` verifier at `xhigh`, on every PR, and reuses it for no later brief. `~/.xum/AGENTS.md` names this rule for verifiers, so the `swarm workers` row does not set their model. No second verifier runs: he ended the `openai:gpt-6.1-sol` verifier on 2026-11-10. When a crash or a refusal ends the verifier, its replacement runs on `anthropic:claude-sonnet-5-5` at `xhigh`. When the ended verifier ran on Sonnet, the replacement runs on Opus, with the brief reworded as defensive checks. When that Opus verifier also ends that way, the root asks him. The merge waits for the verifier's `VERDICT` line on the head. When a push replaces a head, the root sends a new brief for the new head, unless a rule here or in the playbook carries the verdict to it (such as the regenerated-file rule). Apart from his stop order, the root stops a verifier only when every head in that verifier's brief has a new head or has merged. A long silent run is normal. The root never replaces a verifier because it is slow or silent. When a verifier looks stuck, the root tells him and he decides. (In November 2026, two blind judges scored 45 and 44 of 48 PR heads that all three models had checked. Opus found 14 of 15 and 18 of 19 valid blockers, Sonnet 12 and 13, and gpt-6.1-sol 8 and 10. No model found a blocker that Opus missed. Opus also blocked 43 to 47% of the heads without a blocker, so the verify brief below aims to fix its calibration. On the 25 heads with cost data for all three, gpt-6.1-sol cost a median 0.26 USD per check, Sonnet 0.90 USD and Opus 1.44 USD.)
- Every verify brief asks for one table row per finding, with an ID, file:line, a class, the trigger, the evidence, and its origin. The origin is one of four values: introduced, copied (the PR copies a defect from other code), newly reached (the base had it, and the PR makes it reachable), or pre-existing and not reached. The brief sets these rules for the verdict:
  1. ISSUES needs at least one finding in an impact class: a security flaw, data loss, broken core behavior, a rule or doc that a user follows into a wrong result, or a claimed code fix or runtime config fix that no test catches (the mutation rule below, which sends a deployment config fix to the live lane instead). The trigger names the input or the sequence that causes it. The evidence is command output, a quoted file:line, or a run that reproduces it. Every other finding is minor and never changes the verdict.
  2. Before the verifier picks a class, it writes what goes wrong, for whom, and under which sequence. A finding with a concrete path to a result in one of the rule 1 classes is in that class, even when the path is rare. A wrong result outside those classes is minor. A wording or style problem is minor.
  3. A check that did not finish goes into a "not run" list, never into a reason for ISSUES: it timed out, a tool is missing, or it failed at setup on the head and the base alike (the setup rule below). The root reruns or checks each item on that list itself. The merge waits until each item passes its rerun or the root's check, or until he waives that item. A test that fails only under load, its own timeout included, is a finding. The verifier judges it by what its failed assertion claims, under rule 2. Its origin is introduced unless the same test fails the same way on the base.
  4. A wrong claim in the PR body goes into a "body fixes" list. The root edits the body before the enqueue.
  5. When the diff adds or changes a rule or a protocol that several actors follow (roots, processes or workers), the verifier lists the orders in which those actors can act and checks each one.
  6. The `VERDICT` line follows from the table: ISSUES when at least one row is in an impact class and its origin is introduced, copied or newly reached, else PASS. A pre-existing impact finding that the PR does not reach is loop work for a follow-up PR.
  7. The verifier's mutation check makes one mutant per claimed fix and one per production break that the trail records for an added test. On a later head, it runs cut mutants only for tests added or changed since the last verified head. It runs each mutant against every test folder that "Checks for the touched paths" names. A test that the diff adds (a function, a subtest, a table row or an assertion in an existing test) is a cut only when each mutant that turns it red also turns a remaining test red, and it guards no contract in test-audit's retention bar that a remaining test does not also guard. A mutant's run can stop once a test that the diff did not add turns red, and a run that stops this way counts as finished. A run for a trim continues until the narrower added test is red too. An added test with no recorded production break is not a cut: the list names it as missing its failing run. A cut on this list never leaves a mutant with no red test. When the added test sits at a narrower layer than the remaining one, the list names the broader assertion to trim instead, and a trim passes the same checks as a cut. The cuts go into a "test cuts" list and do not change the `VERDICT` line. A mutant run for cuts that does not finish gives no cuts, and it is not a "not run" item. This exemption covers only the cuts: the claimed-fix check under the mutation rule still names a red test, and an unfinished claimed-fix run goes into the "not run" list. The owner applies each cut and trim in the fix push that it holds, or writes in the trail why a kept one is wrong as a cut, such as a behavior that no mutant covers. When no fix push is due, the cuts get a push of their own in review rounds 1 to 3, else a follow-up PR in the same run. (Missing tests gave ISSUES and extra tests only a minor finding, so owners wrote a test for every claim.)

  (In the same judgment, Opus blocked on load-flaky gates, unfinished runs and PR-body receipts. Sonnet named real blockers as nits and passed. All three models missed a cutoff race between roots that Codex found later.)

It never reports "nothing changed" after a wake. A verifier, or a lane that the root briefs, starts no bash job with a monitor and waits in a foreground bash per "CI waits", as owners do.
- A loop is a run of rounds with a stop rule. In a loop whose verifiers raise follow-ups, "a problem the PR's base already has" means the commit where the loop started, not current trunk. A regression the loop introduced is always loop work. A valid review finding from any source (a verifier or lane, an advisor, Codex, a trail review, a bug bash, a PR reviewer or your own check) is loop work too, whether the loop introduced it or main already had it. Fix it in the current PR while rounds allow. Otherwise fix it in a follow-up PR that you drive to merged in the same run. Never put it in a parking or tracking issue unless he agreed to defer it as scope creep (see "Fix now"). A reasoned decline of an invalid finding is still fine. A finding is invalid only when its problem is not real. A bad suggested fix calls for another fix, such as removing the feature, not a decline. The loop stops only when no valid finding is left unfixed, apart from one that he agreed to defer. (An overwrite that one PR introduced was later called a known gap on main. Issue #15 parked 9 valid leftovers. He had them shipped in 3 PRs, plus 1 PR for their review leftovers. A root declined a hint-quoting nit because POSIX quoting does not fit PowerShell, and Codex later raised the same problem as a P2.)
- Every lane that the root briefs follows one result contract. What a lane judges against, such as a credential's threat model or an input's intended behavior, is written down before the lane runs: the owner writes it into the trail, unless a repo file such as the spec already holds it. A lane only reads it. A lane passes only with evidence that its check reached the PR's change. Its result carries to a later head when no change since the head it ran on touches anything the result depends on. A file that a repo tool regenerates follows the regenerated-file rule under "Re-check that the verdicts still describe the code". Run a lane again when anything its result depends on changes. A lane that applies to the PR counts as "not run" when it has no result on the final head, run there or carried there: it could not run, could not show that evidence, or gave no result. "Not run" blocks the merge until a rerun passes or he waives that lane for that PR. (On personal-plugins#27, Codex's round 4 found four ways a lane could let a PR merge on a result that did not hold for its final change.)
- A lane's runtime bug claim (the product does or fails to do something when it runs), or its claim that such a problem is pre-existing, needs evidence as strong as a pass: uncut command output, or a screenshot that the lane opened, plus the path of its repro script. A static finding, such as a spec clause or a doc line that the code contradicts, keeps its file:line evidence. Before the root starts work on such a claim, it asks the reporter for the exact steps in one message. (A claim that a card click did nothing rested on a click run with `>/dev/null 2>&1` and a snapshot cut by `head`. It reached the user, the advisor and a follow-up owner, who did not reproduce it in 8 setups.)
- A test that fails before it reaches the code under test (an import, module or harness setup error), on the head and on the base alike, counts as "not run", never as "pre-existing". The lane names the setup error and checks memory for it first. (Lanes called 66 tests "fail the same on base". Most of them died at setup on a poisoned host cache that memory already described.)
- The test and verification claims in a PR body are receipts. When a valid finding from any review source that the loop rule above names contradicts such a claim, edit the body before the enqueue. (A body kept "a full unit run of 10,259 tests" after a lane showed that the run covered only the feature folders.)
- Add a spec lane. It checks the diff against each numbered decision of the governing spec or RFC. (Behavior tests alone passed a PR that broke one.) Run the lane again when either head changes. A health endpoint never counts as the live lane. (A dependency PR checked only by `/api/health` broke every Workflow run for about 40 minutes.)
- Every verify brief for a code fix asks the verifier to revert or mutate each claimed fix and to name the test that turns red. A code fix that no test catches gets ISSUES for a missing test. A config fix that changes runtime behavior (parsing, validation, a non-default option) gets this mutation check too. A docs fix is checked by the claim lane, and by the execution lane under the rule below. A deployment config fix is checked by the live lane. (Verifiers that broke each fix found three missing tests in two PRs.)
- A docs PR that tells readers to run commands, and any PR that adds a user-facing command or flag, also gets an execution lane, before its Codex loop: a fresh agent follows the doc on a scratch clone of a real target repository. For a new command or flag, the agent runs it under the canary lane's sandbox and canary rules, on the matching surface that the Feature amendment defines, with each example that the docs give for it. It skips or fakes every command that acts outside that clone, such as `gh`, `kubectl` or a deploy, and reports each one it skipped. Run it only when you trust the PR's author, such as his own agents or his team: a doc from anyone else gets the claim lane only. Run it again on the final head when a later edit changes an instruction it follows. (An adoption page passed 3 Codex rounds. - A PR whose diff can change who can read a credential, where, or for how long gets a canary lane. It runs only when you trust the PR's author, as the execution lane does. Otherwise it reports "not run". A fresh agent runs the head only in a throwaway sandbox that reaches nothing on the host or the network outside itself. - A PR whose diff can change an input that decides who can read a credential, where, or for how long gets an input lane, under the canary lane's author, sandbox and canary rules. A finding is any state of such an input under which a canary has a reader, place or duration that its threat model does not allow, or the code does not do what the trail's intended behavior for that input says. (A checker reused across three PRs passed two of them, and only a fresh advisor found that an unset port sent the token to port 80.)
- An evidence script prints one short line per result and ends with a count line. A receipt without its count line is unchecked. (The bash tool dropped an over-long line, and 111 failures read as a pass. Tool request: coder/xum#7876.)

[pstack skills/poteto-mode/playbooks/autopilot-full.md § Run the root layer]

- Count an area's findings from every source (verifiers, advisors, Codex and dogfood runs), across every PR and follow-up PR that reopens that area. An area is one shared asset or invariant, such as one credential, across every PR that touches it, not one file or one PR. Write the tally into the trail at each round boundary. At the second round with findings in the area, when that round has no fewer new findings in the area than the first such round, propose to remove the mechanism, as the round-2 rule in his memory says ("If round 2's findings don't shrink"). By the fourth review round with findings in one area, stop asking for a waiver per round. Ask the operator one question whose options include narrowing the scope or redesigning that area. When he picks a narrowing or redesign option, write the banned premise, and the premise that the findings share, into `owner-rules.md` at once. When you close an area, write the banned premise (such as "no proxy for editor state that has no API") into the repo's AGENTS.md in the PR that closes the area (create it if absent), and into every later owner, verifier and lane brief for that area. In a repo you do not own, put it in the closing PR body and every later owner, verifier and lane brief. - At every round boundary and after every context rollover, load this skill, read his memory and the playbook again, and run `scripts/check-drift.sh`. Check the checkpoint's flow against the playbook step by step. The checkpoint opens with that reload list and copies each per-round rule word for word with its command (status page, spend from `session-usage.json`, trunk CI). It never marks a rule optional or rewords it. Rebuild the owner, verifier and advisor briefs from the trail. Keep the verifier and advisor brief rules in a trail file too, like `owner-rules.md`. ## Changing this skill

`/reflect` and `/correct` lessons about pstack or egm go here, never into the installed plugins (`~/.xum/plugins/`, or `~/.mux/plugins/` on older installs). A general rule goes in a theme section. A rule that changes one plugin step goes under Amendments, with its anchor and the incident that taught it in one line. When a script starts to enforce a rule, replace the prose with "run <script>". Edit in a clone of `ThomasK33/personal-plugins`, run `scripts/check-drift.sh` and the repo validator, and open a PR. When the check exits 1, read each report line before `--accept`:

- `CHANGED`: read that file's `--diff`.
- `ADDED`: read the whole file.
- `ANCHOR`: the plugin dropped or renamed that step. Re-anchor each rule there to the renamed step, or delete it as stale. On a `MISSING` file, handle it as `MISSING` instead.
- `MISSING`: check whether the file exists upstream. Take the plugin's entry in the `plugins.json` that the check's summary line names. It is in `$XUM_ROOT` or `$MUX_ROOT` when set, else in `~/.xum` (`~/.mux` on older installs). Look in the repo at `source.url`, with any trailing slash and `.git` dropped, at commit `lockedSha`. For a `git@github.com:` or `ssh://git@github.com/` source, use `https://github.com/` instead. The path is `<source.subpath>/<path>` when `subpath` is set, else `<path>`. pstack sets `subpath`, and without it the check gets 404 for a file that exists. If the file exists, the install is broken. Fix the install and run the check again. An `ANCHOR` on that file is not stale. If it does not, the plugin dropped or moved the file. Re-anchor each rule on it to the new path, or delete it as stale. For a `WATCH` file, update or remove its `WATCH` entry in `scripts/check-drift.sh` instead, and the same path where steps 1 and 2 name it. Then run the check again. `--accept` refuses while any file is MISSING.
- `NOPIN`: the plugin has no pin to diff against. Read each of its files whole, as for `ADDED`: each anchor path of that plugin in this skill, plus each `WATCH` entry for that plugin in `scripts/check-drift.sh`.

Apply the stale-rule test from "Amendments to plugin steps" to each amended step you read. This skill edit deletes or re-anchors each stale rule. Then run `--accept` and commit `PINNED` in the same PR. `--accept` pins whole plugins, so never run it after reading only some files.
